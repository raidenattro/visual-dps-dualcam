## 三、预算（为什么 2 路必积压）

pose：**7.5Hz × 左右路** = 每巷道 **15 条** Redis Stream 消息/秒。

用 aisle1 / aisle3 的 `pose:snapshot` 在本机跑 `DualcamProcessor`（窗预热后稳态）：

| 场景 | 3D 调用 | 实测 | 每秒 CPU 时间 |
|------|---------|------|----------------|
| 1 巷道，配对成功 | 7.5 × `process_pair` | **45–52ms**（p95 ~80ms） | ~380ms/s → 约 0.4 核 |
| 1 巷道，经常配不上 | ~15 × `process_single` | **48–55ms**（几乎一样贵） | **~750ms/s** |
| 2 巷道进**同一** worker | 上面 ×2 | — | **0.8–1.5 核** → 积压 |

现场 docker stats（aisle1@B + aisle3@A，各 1 巷道）：

| 容器 | CPU |
|------|-----|
| `visual-dps-event-worker` | ~60–62% |
| `visual-dps-event-worker-b` | ~67–70% |
| `visual-dps-infer-{1,2,5,6}` | 各 ~40–50% |

推理侧写得上；积压在 worker 消费。同一进程再进第二条巷道，数学上超过 1 核。

## 四、一帧拆开（aisle1 snapshot，1 人）

`process_pair` ≈ **50ms**，**不是**三角化/贴墙：

| 步骤 | 每帧 | 约占比 | 代码 |
|------|------|--------|------|
| **2D 因果平滑 L+R** | **~34ms** | **~65%** | `LivePose2DSmoother.update` → `smooth_pose2d` |
| **3D 因果平滑** | **~24ms** | **~45%** | `LivePose3DSmoother.update`：整窗 `deepcopy` 两遍 + `smooth_frames` |
| 抬 17 关节 + `contact_slots` | **~2ms** | ~4% | `lift_point` / 32 货格 |
| `json.dumps(result)` | 0.3ms | — | event ~3KiB |
| `publish_event_frame` × L/R | **~4.4ms** | — | **每次 `from_url` 新建连接**再 `close` |

（2D+3D 加总会略大于 50ms，插桩有额外开销，量级正确。）

平滑窗：`LIVE_KEEP_S = 2.4s` → 7.5Hz 下约 **14 帧**。每帧对整窗重跑；`_gauss_smooth` 是纯 Python 双层循环。3D 窗 `deepcopy` 约 **1.8ms/次**。这是 0901 从 dump（25fps 整段）搬到直播的代价。

`process_single`（单路预览）同样走 2D 平滑 + 抬点 + 3D 平滑，**并不便宜**，只是不报贴墙。

## 五、架构上再砍一刀的点

### 1. 消费串行，且 `XREADGROUP count=1`（最大头）

`services/event_engine/worker.py` `_stream_loop`：**每次只取 1 条** pose，`asyncio.to_thread(process_*)` 完，再 `to_thread(publish)` 两次，才读下一条。同一 worker 上两条巷道的消息在一个 event loop 里排队，没有并行。

compose 里虽有 `POSE_STREAM_READ_COUNT=16`，**代码未读该变量**。

### 2. 每条 pose 重新扫巷道 JSON

`grouped_cameras()` 每个 payload 调一次：`list_aisles` 读全部 aisle 文件，再对每个 `load_aisle` **再读一遍**。4 条巷道约 **2.7ms/次**。15 pose/巷道/秒 → 白烧 ~40ms/s，巷道变多线性变差。

顺带：`_refresh_pair_window()` → `pair_window_sec()` 每条 pose 读 `runtime_config.json`（约 0.22ms）。

### 3. L/R 经常配不上，失败路径仍做全量 3D

配对窗日志 **0.400s**（`pair_window_periods=3` × pose 周期 0.133s）。现场左右路 `ts` 差经常 **0.6–1.2s**，于是 `process_single`。

`_note` **5 秒节流**，日志看起来偶尔一条，**实际几乎每帧都在算**。配不上 ≈ 7.5Hz × 2 路 × 50ms → **每巷道 ~0.75 核**，比配对成功的立体更伤吞吐。

### 4. 分片不均

`crc32(aisle_id) % 16`，不是负载均分。A 默认扛 aisle2/3/4，B 几乎只吃 aisle1。开「两条巷道」很容易两条都砸在 A 上（例如 aisle3+aisle4）。

## 七、若以后要加吞吐（只记方向，本日未改）

收益从大到小：

1. **平滑**：直播不要每帧重跑 2.4s 窗；One Euro / 只留 2–3 帧；preview 可不跑 3D 平滑。单项就可能把 50ms 砍到十几毫秒以内。
2. **配不上不要按 15Hz 做全量 3D**：等对侧或降频 preview；失败路径不要和 `process_pair` 一样贵。
3. **消费**：`XREADGROUP count>1`，按 `aisle_id` 批量配对；同一 worker 内两条巷道不要互相堵。
4. **缓存** `grouped_cameras`（按 mtime）；复用 Redis 连接发 overlay。
5. **分片**：CRC32 倾斜时按巷道 sticky 到空闲 worker，或显式指定 shard。

**定性：** 单巷道 7.5Hz 已经贴着 worker 算力墙；再开一路（尤其落到同一容器）不是「再挤一挤」，是超过 1 核。要扩路数必须先砍平滑/串行，而不是再降 pose。
